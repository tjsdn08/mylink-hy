# MyLink 제품·디자인·개발 통합 기준 및 정합성 점검

> 기준일: 2026-11-12 · 기준 브랜치: `main` · 검토 범위: PRD, 사용자 시나리오, 와이어프레임, 디자인 레퍼런스, 실제 소스 코드 및 Firestore 보안 규칙

## 1. 공통 제품 기준

**제품 정의:** MyLink는 Google 로그인을 통해 자신의 소개 및 여러 외부 링크를 관리하고, `/{username}` 공개 페이지 하나로 공유하는 개인 링크 허브다.

**가장 중요한 사용자 가치:** (1) 페이지를 쉽게 만든다. (2) 링크를 쉽게 관리한다. (3) 공개된 결과를 예측하고 공유할 수 있다.

### 문서의 역할과 우선순위

| 질문 | 우선 기준 | 보조 근거 |
| --- | --- | --- |
| 무엇을 최종 구현해야 하는가? | `docs/PRD.md`의 확정 요구사항 | 사용자 결정 및 사용자 시나리오 |
| 사용자가 어떻게 이동하는가? | `docs/USER_SCENARIOS.md` | IA/와이어프레임 |
| 화면과 문구가 어떻게 보여야 하는가? | 아래 MyLink 제품 디자인 원칙 및 공통 컴포넌트 | `docs/WIREFRAMES.md`, `design.md` |
| 지금 실제로 제공하는 기능은? | `src/`, `firestore.rules`, `package.json` | `README.md`, `GEMINI.md` |
| 무엇을 검증해야 하는가? | `docs/FINAL_TEST_CHECKLIST.md` | 기능별 수용 기준 |

**중요:** 코드에 없다는 이유로 PRD의 확정 요구사항을 삭제하지 않는다. PRD는 목표, 이 문서의 진행 현황은 실제 구현을 나타낸다. 문서·코드의 차이가 있으면 ‘미구현/부분 구현’으로 표시한다.

## 2. 최종 MyLink 디자인 원칙

- **색상:** 실제 서비스의 크림·라임·차콜·코랄 중심 팔레트를 제품 브랜드로 사용한다. 현재 UI는 초기 PRD의 ‘화이트·블루’ 시안과 다르며 이 문서의 **실제 브랜드 기준**을 우선한다.
- **디자인 시스템:** `src/app/globals.css`의 실제 CSS 토큰, `src/lib/profile-design.ts`의 프로필 테마, `src/components/ui/`의 재사용 컴포넌트가 구현 기준이다.
- **Toss 참고 범위:** `design.md`는 초기 디자인 리서치·접근성·간격·피드백 패턴의 참고 자료다. Toss의 블루 팔레트 및 모든 시각 요소를 MyLink에 강제하지 않는다.
- **브랜드 표기:** 서비스명은 'MyLink', 로고는 기존 'mylink.'를 유지한다. 한국어 화면 문구는 해요체로 작성하고 ‘프로필’, ‘링크 관리’, ‘공개 페이지’, ‘미리보기’, ‘저장’을 통일한다.
- **레이아웃:** 랜딩의 서비스 소개·이용 방법 본문은 유지하되 헤더 메뉴 링크만 제거한다. 관리 화면은 데스크톱 편집+미리보기 2열, 모바일은 편집을 우선한다. 별도 모바일 브라우저 실측이 필요하다.
- **디자인 동기화:** 랜딩 예시·온보딩·관리 미리보기·공개 페이지는 `ProfileVisual` 공통 컴포넌트를 사용한다. **미리보기만** 공통 폰 프레임과 보이지 않는 내부 스크롤바를 갖고, 실제 공개 페이지는 폰 프레임을 쓰지 않는 전체 웹페이지 구조다. 랜딩·온보딩·관리의 휴대폰 미리보기는 공통 `ProfilePhoneFrame`의 고정된 460/520px 높이 내에서 스크롤한다. 화면 내용 축소 및 잘림 연출을 금지한다. 관리 미리보기는 저장 전 편집값을 보여주고, 실제 공개 페이지는 저장된 값만 표시한다. 미리보기 아래 중복 안내 문구와 공개 페이지 열기 링크는 두지 않는다.
- **기본 테마:** 크림·라벤더·미드나잇. 색상 대비, 터치 타깃, 키보드·스크린리더 피드백을 유지한다.

## 3. 실제 라우팅과 데이터 구조

### 현재 운영 경로

| URL | 현재 역할 |
| --- | --- |
| `/` | 비로그인 랜딩, 신규 회원 온보딩, 로그인 상태에서는 대시보드 |
| `/dashboard` | 링크·조회 현황 및 관리 메뉴 대시보드 |
| `/mypage?tab=links` | 프로필·링크·디자인 탭형 관리 화면 (tab=links/profile/design) |
| `/stats` | 인증된 사용자 통계 화면 |
| `/[username]` | 공개 프로필, 공유·QR·OG |
| `/links` | 과거 데모 URL. 현재는 `/`로 이동 |

`/dashboard`는 현재 구현됐습니다. 독립 `/login`, `/onboarding`, `/dashboard/settings` 및 `/dashboard/*` 세부 편집 경로는 미구현이고, 신규 사용자 온보딩은 `/`에서 조건부로 표시됩니다.

### 현재 Firestore 주요 경로

- `users/{uid}`: 계정 기본 정보, 소유자만 읽기/쓰기
- `users/{uid}/profile/main`: 공개 프로필 및 디자인 필드
- `users/{uid}/links/{linkId}`: 링크와 카운터. 소유자는 전체 열람, 비로그인 방문자는 `isActive=true` 링크만 열람 (최신 규칙 게시 필요)
- `users/{uid}/metrics/profile`: 프로필 조회 수
- `usernames/{username}`: 고유 주소의 UID 매핑

SNS는 별도 `socialLinks` 서브컬렉션이 아니라 **프로필 문서의 배열**로 저장한다. 현재 링크 데이터는 `isActive`, `isFeatured`, `group`, `thumbnailUrl`을 사용한다.

### 우선순위

1. **P0 (사용·보안):** 최신 Firestore Rules 게시, 신규 온보딩·비활성 링크 차단·탈퇴 검증. Cloud Storage는 사용하지 않음.
2. **P1 (검증·안정성):** 탈퇴 백엔드 오케스트레이션/재시도, 저장 전 링크 폼 미리보기의 취소·저장 동작, SNS 모바일 드래그 검증. 이미지 직접 업로드는 Spark 과제 범위에서 제외.
3. **P2 (완성도):** 모바일 UI 검증, 문구/라벨 통일, 접근성, 실제 OG 공유 테스트.

> P0/P1/P2는 구현 순서 제안이며, 미구현 기능을 구현 완료로 표시하는 근거가 아니다.

## 5. 공통 사용자 흐름 (목표와 현재 차이)

**목표 사용자 흐름:** 랜딩 → Google 로그인 → 신규 사용자 필수 정보 설정 → 관리 화면 → 링크/소개/디자인 편집 → 저장 → 미리보기와 실제 공개 URL 비교 → 공유 → 클릭 통계.

**현재 구현 흐름:** 랜딩(스크롤 예시 미리보기) → Google 로그인 → 신규 사용자 `/`의 온보딩(스크롤 실시간 미리보기) 또는 기존 사용자 대시보드 → `/mypage?tab=...` 편집 → 저장 → 공개 URL 공유 → `/stats` 통계 확인.

**공통 작업 규칙:** 다음 개발에서는 목표 흐름을 완성하되 이미 구현된 링크·디자인·공개 프로필 로직을 재작성하지 않는다. 필수값이 비어 있는 신규 사용자와 이미 username이 있는 기존 사용자를 반드시 구분한다.

## 6. 검증 원칙

1. 타입 검사, ESLint, Next.js 빌드는 자동 검사.
2. 로그인, username 충돌, 쓰기 권한, 공개 조회, 저장 전/후 비교는 **실제 Firebase 계정**으로 검증.
3. 화면 정합성은 랜딩 예시·관리 미리보기·공개 프로필을 모바일 320/375px, 태블릿, 데스크톱 및 다크 모드에서 확인.
4. Firestore Rules 변경 후에는 **Firebase Console 게시 여부**와 비활성 링크 차단·탈퇴를 테스트. 프로필 이미지는 Google 계정 사진으로 확인.
5. `docs/FINAL_TEST_CHECKLIST.md`의 미검증 항목은 검사 완료라고 주장하지 않는다.
6. 신규 기능의 완료 판정은 PRD 수용 기준 + 사용자 시나리오 + 화면 검증 + 보안 규칙을 모두 만족할 때에만 한다.
