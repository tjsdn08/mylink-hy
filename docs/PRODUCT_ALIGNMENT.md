# MyLink 제품·디자인·개발 통합 기준 및 정합성 점검

> 기준일: 2026-11-12 · 기준 브랜치: `main` · 검토 범위: PRD, 사용자 시나리오, 와이어프레임, 디자인 레퍼런스, 실제 소스 코드 및 Firestore 보안 규칙

## 1. 공통 제품 기준

**제품 정의:** MyLink는 Google 로그인을 통해 자신의 소개 및 여러 외부 링크를 관리하고, `/{username}` 공개 페이지 하나로 공유하는 개인 링크 허브다.

**가장 중요한 사용자 가치:** (1) 페이지를 쉽게 만든다. (2) 링크를 쉽게 관리한다. (3) 공개된 결과를 예측하고 공유할 수 있다.

### 문서의 역할과 우선순위

| 질문 | 우선 기준 | 보조 근거 |
| --- | --- | --- |
| 무엇을 최종 구현해야 하는가? | `docs/PRD.md`의 확정 요구사항 | 사용자 결정 및 사용자 시나리오 |
| 사용자가 어떻게 이동하는가? | `docs/USER_SCENARIOS.md` | IA/와이어프레임 |
| 화면과 문구가 어떻게 보여야 하는가? | 아래 MyLink 제품 디자인 원칙 및 공통 컴포넌트 | `docs/WIREFRAMES.md`, `design.md` |
| 지금 실제로 제공하는 기능은? | `src/`, `firestore.rules`, `package.json` | `README.md`, `GEMINI.md` |
| 무엇을 검증해야 하는가? | `docs/FINAL_TEST_CHECKLIST.md` | 기능별 수용 기준 |

**중요:** 코드에 없다는 이유로 PRD의 확정 요구사항을 삭제하지 않는다. PRD는 목표, 이 문서의 진행 현황은 실제 구현을 나타낸다. 문서·코드의 차이가 있으면 ‘미구현/부분 구현’으로 표시한다.

## 2. 최종 MyLink 디자인 원칙

- **색상:** 실제 서비스의 크림·라임·차콜·코랄 중심 팔레트를 제품 브랜드로 사용한다. 현재 UI는 초기 PRD의 ‘화이트·블루’ 시안과 다르며 이 문서의 **실제 브랜드 기준**을 우선한다.
- **디자인 시스템:** `src/app/globals.css`의 실제 CSS 토큰, `src/lib/profile-design.ts`의 프로필 테마, `src/components/ui/`의 재사용 컴포넌트가 구현 기준이다.
- **Toss 참고 범위:** `design.md`는 초기 디자인 리서치·접근성·간격·피드백 패턴의 참고 자료다. Toss의 블루 팔레트 및 모든 시각 요소를 MyLink에 강제하지 않는다.
- **브랜드 표기:** 서비스명은 'MyLink', 로고는 기존 'mylink.'를 유지한다. 한국어 화면 문구는 해요체로 작성하고 ‘프로필’, ‘링크 관리’, ‘공개 페이지’, ‘미리보기’, ‘저장’을 통일한다.
- **레이아웃:** 랜딩은 짧고 명확하게, 관리 화면은 데스크톱 편집+미리보기 2열, 모바일은 편집을 우선한다. 별도 모바일 브라우저 실측이 필요하다.
- **디자인 동기화:** 랜딩 예시·관리 미리보기·공개 페이지는 `ProfileVisual` 공통 컴포넌트를 사용한다. 관리 프리뷰와 공개 프리뷰에서 실제 저장값이 다를 수 있다는 점을 명확하게 안내한다.
- **기본 테마:** 크림·라벤더·미드나잇. 색상 대비, 터치 타깃, 키보드·스크린리더 피드백을 유지한다.

## 3. 실제 라우팅과 데이터 구조

### 현재 운영 경로

| URL | 현재 역할 |
| --- | --- |
| `/` | 비로그인 랜딩, 로그인 상태에서는 관리 화면 |
| `/mypage` | 프로필·링크·디자인 탭형 관리 화면 |
| `/stats` | 인증된 사용자 통계 화면 |
| `/[username]` | 공개 프로필, 공유·QR·OG |
| `/links` | 과거 데모 URL. 현재는 `/`로 이동 |

PRD 및 와이어프레임의 `/login`, `/onboarding`, `/dashboard/*`, `/dashboard/settings`는 **목표 IA의 개념적 경로**이며 현재 구현된 URL이 아니다. 분리된 대시보드 및 전용 온보딩을 도입할 때 경로와 문서를 함께 갱신한다.

### 현재 Firestore 주요 경로

- `users/{uid}`: 계정 기본 정보, 소유자만 읽기/쓰기
- `users/{uid}/profile/main`: 공개 프로필 및 디자인 필드
- `users/{uid}/links/{linkId}`: 링크와 카운터, 공개 읽기 허용
- `users/{uid}/metrics/profile`: 프로필 조회 수
- `usernames/{username}`: 고유 주소의 UID 매핑

SNS는 별도 `socialLinks` 서브컬렉션이 아니라 **프로필 문서의 배열**로 저장한다. 현재 링크 데이터는 `isActive`, `isFeatured`, `group`, `thumbnailUrl`을 사용한다.

## 4. 요구사항-화면-개발 간 정합성 목록

| ID | 기능/요구사항 | 현 상태 | 정합성 문제 및 다음 작업 |
| --- | --- | --- | --- |
| A01 | Google 로그인 | 구현, 운영 검증 필요 | 신규 가입 완주 테스트 |
| A02 | 필수 username·표시 이름 온보딩 | **부분 구현** | 프로필 편집에서 저장 가능, 초기 안내 추가. 최초 설정 전 관리자 기능 접근 차단 및 별도 온보딩은 미구현 |
| A03 | 고유 username 중복 방지/변경 | 구현, 검증 필요 | Firestore 트랜잭션과 변경 전 주소 해제 확인 |
| A04 | 링크 CRUD·삭제 확인 | 구현 | URL·오류·삭제 테스트 |
| A05 | 링크 정렬 및 모바일 터치 | **부분 구현** | sortOrder 자동 저장, 위/아래 버튼. 모바일 드래그 UX 수동 검증 |
| A06 | SNS 추가·수정·삭제 | 구현 | 별도 편집 영역 대신 디자인·SNS 탭에서 플랫폼별 URL 관리 |
| A07 | SNS **사용자 지정 순서** | **미구현** | 현재 고정 플랫폼 순서. 정렬 UI·저장 정책 추가 필요 |
| A08 | 프로필 사진 **직접 업로드** | **미구현** | 현재 Google 사진 표시. Firebase Storage 업로드/규칙 없음 |
| A09 | 개인별 테마·색상 | **부분 구현** | 테마·배경색·커버·버튼 모양 지원. PRD의 별도 버튼색·텍스트색 조절은 미구현 |
| A10 | 저장 전 실시간 미리보기 | 구현, 검증 필요 | 링크 생성·수정 폼의 저장 전 반영 범위를 별도 검증 |
| A11 | 공개 페이지/URL/QR/OG | 구현, 운영 검증 필요 | OG 크롤러·모바일·QR 외부 요청 검증 |
| A12 | 조회 수·링크 클릭 수 | 구현, 운영 검증 필요 | 반복·봇 요청 제한 없음. ‘순 방문자’로 표현 금지 |
| A13 | 비활성 링크 신규 클릭 차단 | **규칙 개선 반영** | `firestore.rules`에 비활성 카운터 차단 추가. Firebase Console에 게시해야 실제 적용 |
| A14 | 숨김 링크 비공개 보호 | **미충족** | 화면에서만 숨김. 컬렉션 공개 읽기로 URL은 조회 가능. 비밀 URL 등록 금지 안내 유지 |
| A15 | 계정 탈퇴 및 데이터 일괄 삭제 | **미구현** | Auth·Firestore·이미지 정리 및 실패 재처리 설계 필요 |
| A16 | Zustand 상태 관리 | **설계 변경** | 실제로 React state/Context/Firestore 사용. 억지로 Zustand 도입하지 않음 |
| A17 | 브랜드 디자인 일관성 | **기준 통합** | 현재 크림·라임 기반 UI를 정본으로 명시. Toss는 참고 자료 |

### 우선순위

1. **P0 (사용·보안):** A02 최초 설정 강제와 안내, A13 Firebase Rules 게시 및 테스트, A14 숨김 링크의 개인정보 위험 검토.
2. **P1 (확정 PRD 기능):** A15 계정 탈퇴, A08 이미지 업로드, A07 SNS 순서, A09 개별 색상 설정, A10 미리보기 범위 검증.
3. **P2 (완성도):** 독립 대시보드 경로, 모바일 UI 검증, 문구/라벨 통일, 접근성, 실제 OG 공유 테스트.

> P0/P1/P2는 구현 순서 제안이며, 미구현 기능을 구현 완료로 표시하는 근거가 아니다.

## 5. 공통 사용자 흐름 (목표와 현재 차이)

**목표 사용자 흐름:** 랜딩 → Google 로그인 → 신규 사용자 필수 정보 설정 → 관리 화면 → 링크/소개/디자인 편집 → 저장 → 미리보기와 실제 공개 URL 비교 → 공유 → 클릭 통계.

**현재 구현 흐름:** 랜딩 → Google 로그인 → Firestore 사용자/프로필 확인·생성 → `/`의 관리 화면 → username 미설정 시 초기 안내 → 프로필 편집에서 username·표시 이름 저장 → 공개 URL 이용.

**공통 작업 규칙:** 다음 개발에서는 목표 흐름을 완성하되 이미 구현된 링크·디자인·공개 프로필 로직을 재작성하지 않는다. 필수값이 비어 있는 신규 사용자와 이미 username이 있는 기존 사용자를 반드시 구분한다.

## 6. 검증 원칙

1. 타입 검사, ESLint, Next.js 빌드는 자동 검사.
2. 로그인, username 충돌, 쓰기 권한, 공개 조회, 저장 전/후 비교는 **실제 Firebase 계정**으로 검증.
3. 화면 정합성은 랜딩 예시·관리 미리보기·공개 프로필을 모바일 320/375px, 태블릿, 데스크톱 및 다크 모드에서 확인.
4. Firestore Rules 변경 후에는 **Firebase Console 게시 여부**와 실제 비활성 링크 클릭 차단을 테스트.
5. `docs/FINAL_TEST_CHECKLIST.md`의 미검증 항목은 검사 완료라고 주장하지 않는다.
6. 신규 기능의 완료 판정은 PRD 수용 기준 + 사용자 시나리오 + 화면 검증 + 보안 규칙을 모두 만족할 때에만 한다.
